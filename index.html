Install

Write SQL. Get a dashboard.

Write the SQL query you already know how to write, add a few -- @ comments, and asql renders it into a polished, self-contained HTML analytics report. No BI tool, no notebook, no JavaScript, no <div> wrangling. Your SQL runs through an embedded DuckDB engine, with no server to stand up.

$curl -fsSL https://www.asql.dev/install.sh | sh
$docker pull ghcr.io/cuiqanalytics/asql

Free. First dashboard in about 60 seconds. No account, no telemetry.

Apple Silicon? The image is linux/amd64 only: add --platform linux/amd64.

From a prompt to a git diff in 46 seconds

Prompt → readable SQL → dashboard → one-word edit → git diff. No cuts.

A few comments in. A chart out.

Above the query, -- @report names the report and -- @chart: trend names the intent. asql reads the result columns, date, series and value, and draws a multi-series line chart with axes, legend and number formats.

The file is still plain SQL. duckdb < report.sql runs it unchanged.

-- @report
-- title: Revenue Dashboard
-- subtitle: 2026

-- @chart: trend
-- title: Monthly Revenue by Channel

SELECT
    date_trunc('month', d)                AS date,
    channel                               AS series,
    base + date_diff('month', DATE '2025-01-01', d) * growth
        + (random() * 20000)::int         AS value
FROM range(DATE '2025-01-01', DATE '2026-01-01', INTERVAL 1 MONTH) AS t(d),
     (VALUES ('Direct', 190000, 46000),
             ('Paid', 160000, 25000),
             ('Partner', 55000, 26000)) AS c(channel, base, growth)
ORDER BY 1;
$ asql build report.sql
Wrote report.html

See it while you write it.

asql preview report.sql serves the report on localhost:4321. Every save rebuilds it and reloads the open tab. No build step, no refresh.

A broken query shows its error in place of the chart and recovers on your next save. Each chart has an ✎ Edit button: change its chart type, SQL or metadata in the browser, and asql writes the change back to your .sql file.

$ asql preview report.sql
Serving http://localhost:4321 — watching report.sql for changes

Why asql

The chart is inferred, not configured.

Above your query, one comment names the intent: -- @chart: trend, ranking, funnel, waterfall, heatmap and more. asql reads the result shape to pick the mark, axes, series grouping, colors and number formats. No charting API to learn, just a keyword in a comment.

One file in, one file out.

Input is runnable SQL. Output is a single .html with no asset folder. Email it, commit it, drop it on any static host.

It stays SQL.

Every annotation is a -- comment. duckdb < report.sql still works, because asql runs on DuckDB under the hood. The file never stops being valid, runnable SQL.

Two audiences, one source.

The same file builds an interactive dashboard or a print-ready narrative memo. One metadata line switches format.

Simple by default, precise when you need it.

Name your columns date, series, value and most reports need no overrides at all. When one does, add a single line (@x, target, series-color) only where you need it; the defaults never disappear. A Claude Code skill teaches an AI agent the whole syntax, so even the overrides are one prompt away.

Any DuckDB extension, right in your SQL.

A -- @setup block runs before every query, so any community extension you can INSTALL in DuckDB (read spreadsheets, diff tables, attach Postgres or MySQL) is available to every chart in the report.

It's a compiler, not a generator.

AI assistants now build dashboards on request, and they're great for exploring a question. asql is for what comes after you have the answer: a report that has to be reproducible, reviewed, shared with people who don't have a seat, and hosted where your data lives. AI assistants answer the question. asql ships the answer, on your infrastructure.

Self-hosted, end to end.

Queries run in DuckDB on your machine or server, against your files or attached databases. Nothing in the build or the output calls a vendor. Rebuild from cron or CI with the Docker image, publish on an intranet or a bucket. Works air-gapped.

The query is the dashboard.

Other tools show you the SQL behind a chart so you can check it. In asql the SQL is the source, and the chart is compiled from it.

Same input, same output, every time.

A prompt-generated dashboard is a fresh one-off each time you ask. Re-run it and you may get a different layout, different chart choices, different code. asql build report.sql renders the same result every time.

Still just SQL, not a new app to maintain.

A generated dashboard is either a new codebase (React, config, glue) that only the AI that wrote it really understands, or it lives inside someone else's app. Changing an asql report means editing the query you already had.

Diffable and reviewable.

git diff report.sql is a SQL diff anyone can read. No generated UI code to review.

No runtime you depend on.

One static .html file: no hosted app, no seat or vendor account to view it, no server in the loop. Open it in five years.

One source, two audiences.

Add one line, -- format: narrative, and the same file builds as a print-ready, single-column document with a table of contents and templated prose that pulls real numbers from the queries.

Same source. Different audience.

Or just ask Claude

asql ships with two Claude Code skills. asql knows the annotation syntax, the chart intents and the column names asql picks up on its own. asql-exec adds a review pass for reports headed to leadership: it leads with the decision and flags buried leads, unsupported claims and charts that mislead. Claude builds the report with asql and checks the result before it hands it over.

$~/.local/lib/asql/install-skills.sh
